# 范例一：Agentic RAG，从功能罗列到可审查的工程叙述

> **示范，不是已核验的个人简历。** 机制与数字取自用户草稿；本仓库未读取其代码或实验日志。以下保守改写只展示如何处理现有陈述。正式使用前仍须完成 Gap Check；未确认的日期与角色不代填。

## 修改前

> 使用 FastAPI 和 LangGraph 开发企业级 RAG 系统，支持上传、混合检索、重排、问答和引用。自研 Runtime，实现双库强一致、流式断点续跑与闭环治理；优化后拒答率从 71.7% 降到 56.5%，显著提高回答准确率。

这段反例故意包含越界写法。调用框架不能证明自研 Runtime，双库不能证明强事务，SSE 回放不能证明计算恢复；拒答率变化也不能证明准确率提升。

## 应先问的四个问题

1. 任务租约、取消与旧任务提交校验分别在哪实现？SSE 重启后恢复的是历史事件，还是生成任务本身？
2. 46 题是预先冻结的题单，还是两次运行的共同题？原始各组多少题，是否排除失败、超时或未评分项？
3. 两次 Dense 运行的模型、提示词、数据/索引版本和判分规则有什么变化？有没有重复运行或策略消融？
4. AI 审阅是否有“应答/应拒”标签与人工复核？哪些代码、测试和回归记录支持实现与修复主张？

## 修改后：保留来源、降低结论强度

## 为什么这样改

“后次较前次低约 15.2 个百分点”来自草稿中已四舍五入的两个比例，不补造分子。正式成稿确认时间/角色后替换占位；确认基线与候选版本后，最好将“两次运行”改为可定位的版本名称。

这里不擅自认定 46 题是独立冻结集，也不擅自认定是事后交集；必须按用户回答命名。两种选择方式可以支持不同强度的结论，不能混用。

不再写“全链路中断恢复”：草稿中的事件回放与真正计算恢复应分别提供证据。也不补写“GPU 利用率”“Recall 提升”“可用性 99.9%”等不存在的测量。

治理段没有擅自增加“所有修复均通过回归”的结果。只有用户确认修复后实际执行了对应回归，才能改成“修复并以对应回归检查是否再现”。

这里的结构是示范，内容不是对实现的认证。正文越具体，越需要本人能解释写入条件、边界状态与数据流。
